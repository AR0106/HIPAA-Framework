* 1) Data-at-rest (SQLite + encrypted CSVs)
** [x] SQLite database encrypted at rest (sqleet)
Evidence: `sql.Open("sqleet", "cdd.db?_key=...")` in `HIPAA Framework/user/user_service.go`

*** DONE Remove hardcoded SQLite encryption key usage anywhere in code
- Current gap: `GetDataEncryptionKey` opens DB with a hardcoded `_key=UWGB2029SecretKey` ignoring caller-provided secret.
- Goal: all DB opens derive `_key` from a single secret source (env var / OS keychain / injected config), never a literal in code.

** [-] Encrypted CSV storage for PHI (per-record AEAD)
Evidence: AES-GCM used in `HIPAA Framework/crypto/crypto_service.go`; called from `HIPAA Framework/data/data_service.go`

*** DONE Enforce strong, correctly-sized encryption keys for AES-GCM
- Current gap: `EncryptData` accepts arbitrary byte slice; upstream may pass weak/short strings.
- Goal: require 16/24/32-byte key (AES-128/192/256), reject others with explicit error.

*** FUTURE Add versioned envelope format for encrypted CSV lines (algorithm + key id + nonce + ciphertext)
- Current gap: ciphertext is base64(nonce||ciphertext) without metadata; rotation/migrations hard.
- Goal: include a small header (version, key identifier) so you can rotate keys and still decrypt old lines.

*** TODO Add cryptographic integrity for whole encrypted-CSV file (not just per-line)
- Gap: AEAD protects each record, but attacker can delete/reorder/rollback lines.
- Goal: add one:
  - manifest hash chain per file (prev_hash || record_bytes)
  - or periodic signed checkpoints
  - or per-file Merkle root stored in DB + audited
- Acceptance: verifier detects deletion/reorder/rollback of records.

*** DONE Tighten filesystem permissions for all PHI-bearing artifacts
- Current gap: data dir `0755`, data files `0644`, `audit.log` `0644` (readable by other users).
- Goal: default to owner-only access on single machine.
- Acceptance:
  - directories: `0700`
  - files: `0600`
  - verified by creating new DB/log and checking mode bits.

*** TODO Prevent PHI leakage via temp files, swap, crash dumps
- Goal:
  - avoid writing PHI to OS temp unless encrypted + `0600`
  - scrub/limit panic dumps (no PHI in panic/error strings)
  - document operational hardening: FileVault on, disable core dumps, restricted backups
- Acceptance: tests/greps show no PHI in logs/errors; temp file usage audited.

* 2) Key management (highest risk in current code)
*** DONE Eliminate all hardcoded secrets/peppers from repository
- Current gaps:
  - password “pepper” literal in `HIPAA Framework/crypto/crypto_service.go`
  - hardcoded DB key literal in `HIPAA Framework/crypto/crypto_service.go`
- Goal: all secrets come from runtime secret source (env var, OS keychain, encrypted config).
- Acceptance: `grep -R` for secret strings and obvious patterns (e.g., `SecretKey`, `_key=`) returns none.

*** DONE Stop using a fixed shared data encryption key for every user/dataset
- Current gap: `dataKey := []byte("abcdefgh12345678")` in `HIPAA Framework/user/user_service.go`.
- Goal: generate unique data keys (per user, per dataset, or per file) with rotation capability.
- Acceptance: registering two users yields distinct DEKs; compromise of one key does not decrypt others.

*** TODO Add key rotation support for DEKs (and ability to decrypt old records)
- Goal: rotate DEKs, mark new key active, keep old keys available for decrypt only.
- Acceptance: after rotation, new writes use new DEK; old records remain readable.

*** TODO Add master key strategy (KEK) + secure storage (macOS Keychain)
- Goal:
  - store KEK in OS keychain (or user-provided passphrase -> Argon2id -> KEK)
  - store DEKs encrypted by KEK in keystore table
  - never store raw DEKs at rest
- Acceptance: DB contains only wrapped keys; app can re-open after restart via keychain/passphrase.

*** TODO Add key lifecycle controls: generation, access logging, destruction (crypto erase)
- Goal:
  - key create/rotate/destroy all audited
  - destroy = delete wrapped DEK + rotate KEK if needed
- Acceptance: after destroy, decrypt fails; audit shows who/when/why.

* 3) Authentication (person/entity authentication)
** [-] Login/registration exists
Evidence: `RegisterUser`, `LoginUser` in `HIPAA Framework/user/user_service.go`

*** DONE Replace deterministic SHA-256 password hashing with Argon2id (or bcrypt) + per-user salt
- Current gap: `HashPassword` is fast/deterministic; vulnerable to offline cracking.
- Goal: use a standard password hash:
  - Argon2id recommended (memory-hard)
  - Store parameters + salt per user
- Acceptance: password hash string encodes algorithm + params + salt; verification constant-time.

*** TODO Add secure credential change flow
- Goal: change password requires current password; rehash with new salt/params.
- Acceptance: password change updates stored hash; old password no longer works; events audited.

*** TODO Add brute-force defenses (rate limit + lockout) + audit
- HIPAA: supports 164.312(d) person/entity auth; also 164.308(a)(5)(ii)(C) login monitoring.
- Goal:
  - per-username + per-IP attempt tracking (if networked)
  - exponential backoff / temporary lockout
  - audit login fail/success + lockout/unlock
- Acceptance: repeated failures trigger lockout; logs show events.

*** TODO Add MFA support (optional but strong) for any UI/app using this library
- HIPAA: addressable; HITECH breach safe-harbor relies on strong encryption; MFA reduces account compromise.
- Goal: TOTP/WebAuthn hooks; at minimum API surface to enforce MFA upstream.
- Acceptance: integration sample shows MFA gate before PHI actions; events audited.
